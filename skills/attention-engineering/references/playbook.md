# Playbook — 可执行改法

每条统一格式：**问题 → 做法 → 输出形态**。挑一条用，不要一次全上。

---

## 1. 长报告 → 决策卡

**问题：** 报告很长，结论埋在中段，人读完才知道要做什么，或者没读完就去做别的事了。

**做法：**
- 只保留会改变决策的内容。判断标准：删掉这一条，读者的行动是否改变。不变 → 删。
- 结构固定为四块：结论 / 证据 / 风险 / 建议动作。
- 完整报告不删除，降级为附录；卡片里给一行指向它。
- 卡片上限 10 行。超了就是还没决定删什么。

**输出形态：**

```
结论：<一句话，可执行>
证据：<2–3 条，每条一行，带数字或链接>
风险：<1–2 条，含触发条件>
建议：<1 个动作 + 负责人 + 是否可逆>
附录：<路径或链接>（含完整数据、过程、备选方案）
```

**判据：** 只读卡片能做出决定吗？能 → 合格。要读附录才能决定 → 证据不足，回去补而不是加长卡片。

## 2. 告警分级与静默

**问题：** 告警太多，团队开始忽略，真故障混在噪声中。

**做法：**
- 定义四层，每层绑定**唯一**的通知通道与响应时限。层级不是标签，是路由。
- 新增告警必须先分类进某一层；分不进去的默认丢弃（并记录）。
- 静默规则写死：同类告警聚合窗口、已知维护窗口、同一根因只报一次首因。
- 每季度审计：哪一层从未被响应过 → 该层规则失效。

**输出形态：**

| 级别 | 条件 | 通道 | 响应时限 | 静默规则 |
|---|---|---|---|---|
| P0 | 用户可见中断 / 数据风险 | 立即叫人 | 15 分钟 | 不静默 |
| P1 | 功能降级，有绕行方案 | 当日报 | 1 个工作日 | 同根因合并 |
| P2 | 趋势异常，暂不影响用户 | 周报 | 1 周 | 全部聚合 |
| 丢弃 | 无法归入以上 | 无 | 无 | 记录，供审计 |

**判据：** 打断预算是有限的（见第 6 条）。新告警挤占预算时必须挤掉旧的，不能扩容。

## 3. 代码审查分层

**问题：** AI 让 diff 变大，人仍逐行看，于是变成快速点「通过」。

**做法：**
- 机器审**面**：格式、lint、测试覆盖、常见缺陷模式、依赖风险、可自动验证的一切。机器结论直接进 PR，不再由人重复。
- 人审**点**：设计取舍、接口契约、影响面、不可逆操作（迁移、删除、发版）、安全边界。
- 单次审查设上限（实践上 200–400 行）。超限就拆 PR，不靠意志硬扛。
- Review 交付按风险排序，不按文件顺序。

**输出形态：**

```
[高风险] <file:line> — <问题> — <建议>
[中风险] <file:line> — <问题> — <可接受，需确认>
已由机器覆盖：lint / 测试 / 依赖 / 格式（详见 CI）
本次未审：<文件范围>（低于风险阈值）
```

**判据：** 人需要回答的问题是「这些高风险点处理了吗」，不是「每一行写对了吗」。

## 4. Agent 输出协议

**问题：** Agent 每次输出几十行，人被迫读完才能知道有没有事。

**做法：**
- **第一行给状态**：完成 / 需要决策 / 阻塞。三选一，不写别的。
- **第二行给地图**：这次做了什么、影响哪里、还剩什么。
- **细节默认折叠**：放附录、文件、或「展开」占位。不要默认铺开。
- **只在两种情况下举手**：需要价值判断，或真的卡住。其余自己闭环。
- 失败也必须收口：说清坏在哪、为什么、已尝试什么、下一步需要谁。

**输出形态：**

```
✅ 已完成：<一句话结果>
影响：<2 条以内>　剩余：<无 / 具体项>
失败时改为：
⚠️ 阻塞：<一句话>　原因：<一行>　已尝试：<1–2 条>　需要：<谁做什么>
```

**判据：** 人是否能在 5 秒内判断「要不要管这件事」。不能 → 第一行没写对。

## 5. 文档交付

**问题：** 交付物是长文，读的人找不到重点，最后只看标题就转发。

**做法：**
- 一张图（结构、流程、或状态机）+ 三个关键决策。其余都是支撑材料。
- 三个决策必须是**已作出的选择**，带理由和代价；不是「待讨论的问题清单」。
- 长文保留为附件，顶部一行说明「本文支撑哪三个决策」。
- 不写「背景介绍」章节。必要的背景压在图的注释里。

**输出形态：**

```
<一张图>

决策 1：<选了什么> — 因为 <理由> — 代价 <代价>
决策 2：...
决策 3：...

未决：<0–1 个真正需要对方拍板的问题>
附件：<路径>
```

**判据：** 读者能否只靠图和三个决策复述这次交付。不能 → 决策没写清，不是图不够多。

## 6. 通知批处理与打断预算

**问题：** 通知实时推送，人被持续切碎，专注时长按分钟计。

**做法：**
- 给每个人设固定打断窗口（每天 2–3 次，如 10:00 / 15:00），非 P0 一律入队。
- P0 的定义必须窄且可验证；P0 滥用一次，整套分级失效。
- 合并同源通知：同一系统、同一根因、同一发布，合并为一条。
- 通知内容自带结论与动作，不要求人点进去才知道是什么事。

**输出形态：**

```
[15:00 汇总] 3 条
1. <系统>：<结论> → <动作 / 无需动作>
2. ...
（P0 走独立通道，不入汇总）
```

**判据：** 统计每天被打断次数。超过预算 → 降级或合并，不允许长期超支。

## 7. 用 skill 替代读文档

**问题：** 知识写在 README 里，每个新 agent / 新人都要读一遍，读完还不一定用对。

**做法：**
- 把「怎么做」装进 skill：触发条件写在 description，判断依据写进正文，细节放 references 按需读。
- README 只留安装与一句话定位，不再承载操作规程。
- 每个 skill 自带判据（什么时候用、什么时候不用），因为误用比不用更贵。
- references 不预加载。加载成本也是注意力成本。

**输出形态：**

```
skills/<name>/SKILL.md          # 触发条件 + 判据 + 速查
skills/<name>/references/*.md   # 深度材料，按需读
```

**判据：** 一个 agent 只读 SKILL.md 能否把事做对。不能 → 判据缺失；能但太长 → 该拆 references。

## 8. 度量

**问题：** 用产出量（报告数、PR 数、告警数）衡量成效，于是系统优化的是产量，不是注意力。

**做法：** 只测四类，且都能从现有数据算出：

| 指标 | 定义 | 差的方向 |
|---|---|---|
| 被处理量 / 产出量 | 真正被读、被决策、被合并的比例 | 产出涨、比率跌 |
| 采纳率 | 建议中被实际执行的比例 | 建议多、采纳少 |
| 打断次数 / 天 | 主动触达人的次数 | 持续上升 |
| 首次理解时间 | 从打开到说出结论的耗时 | 变长即压缩失败 |

**做法细节：**
- 每个指标配一个明确目标值与责任人，否则不会有人看。
- 禁止把「产出量」本身当 KPI。它可以作为分母，不能作为分子。
- 每季度删掉一个没人看的报表 / 没人响应的告警 / 没人用的仪表盘。

**判据：** 如果一项改进无法在这四个指标上体现，它大概不是注意力工程的改进。

## 8. Hierarchical delegation（分层 agent）

**问题：** 并行任务变多后，人同时跟多个 agent 会话，切换成本超过单任务成本。瓶颈不是「人做不完」，是「人跟不过来」——同时跟踪的会话数约 3–5 个就到上限。

**做法：**
- 一个常驻 **Router** 负责收事件、分级、派单。它不执行任务，只做路由与汇总。
- **Worker** 各自独立上下文并行执行，不共享会话，彼此不知道对方存在。
- 人只看 Router 的汇总与阻塞项；Worker 的中间过程不回传到人的视野。
- Router 输出固定为：完成项 / 需决策项 / 阻塞项 / 丢弃项（含原因）。
- 层级可递归：Router 下面还可以有子 Router，但每一层都遵守同一条规则——**向上只报决策与阻塞**。

**输出形态：**

```
人
└── Router（收事件 / 分级 / 派单 / 汇总）
    ├── Worker A  ── 完成
    ├── Worker B  ── 需决策 1 项
    └── Worker C  ── 阻塞（等外部接口）
```

Router 对人的汇报：

```
完成 3 / 需决策 1 / 阻塞 1 / 丢弃 4（原因见附录）
需决策：<一句话 + 选项 A/B + 推荐>
```

**判据：** 人同时在跟 >3 个会话，就该加一层 Router，而不是让人更快切换。加 Router 的判断依据是「会话数」，不是「任务数」——任务再多，只要被收口成一次汇报，人仍然只需要一个注意力槽。

参考实现：`https://github.com/deepseek-ai/dsh-superagent-prototype`（公开仓库）。

## 组合使用

最小可用组合是 **4 + 8**：先把 agent 输出协议固定下来（立刻见效），再用四个指标确认真的省了。其次是 **1 + 2**（报告与告警），因为它们覆盖大多数日常打断。**3 + 6** 适合团队层。不要一次上线超过两条——改太多无法归因，也违反本 playbook 自己的原则。
